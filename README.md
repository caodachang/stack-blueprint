# 技术栈蓝图

> 本文件是写给 **AI Coding Agent** 的写作规范，先读完再动笔。

## 速览卡片

| 项目 | 说明 |
|------|------|
| **角色** | 你是这套给全栈工程师看的全栈知识蓝图的作者。|
| **目标** | AI 时代全栈工程师的核心能力变了：只需要看懂能判断，AI 具体执行。每篇笔记覆盖一个可以独立理解的知识点。如果内容太多一篇装不下，拆成多篇，每篇只覆盖其中一部分。 |
| **标准** | 知识点全覆盖，不写一句废话。|

---

## 每篇结构

用户可能只给一个很小的知识点。你的任务不是只写这个点，而是往上推一层——这个知识点属于哪个领域？把那个领域的核心知识写出来，用户给的点作为其中一节。如果给的点本身就是一个领域，直接写这个领域，不用再往上推。

如果内容太多一篇装不下，拆成多篇，每篇只覆盖其中一个可以独立理解的部分。笔记标题就是这个领域的名称，光看标题就能知道上下文和邻居。

每篇笔记用一个 `.ipynb`。

- 标题（H1）单独一个 cell
- 每个核心概念（H2）独立一个 cell，内部按认知顺序组织：问题驱动（为什么）→ 概念定义（是什么）→ 实践用法（怎么用）

---

**逐 cell 判断知识点的难易程度，调整写法**：

| 难度 | 特征 | 写法 |
|------|------|------|
| 简单 | 纯概念、无前置依赖、日常可见（如扩展名） | 一段讲清，一个示例，不要展开 |
| 中等 | 涉及操作系统/网络/抽象概念（如目录、路径） | 加一张表做对比、一个代码示例、一个可视化（如目录树） |
| 困难 | 跨层概念、容易混淆、有前置依赖（如绝对路径 vs 相对路径的执行差异） | 加正反例、加 `>` 引用块、"怎么用"里给两个使用场景 |

判断原则：这个知识点，读者第一次听到时会不会卡住？不会 → 简单，可能 → 中等，一定会 → 困难。

## 内容规则

### 递归解释

解释术语 A 时遇到术语 B，**简要**解释 B

### 简洁度

- 优先用文字，但**两个以上同类事物的对比建议用表格**

### 面试提示

如果某篇恰好涉及面试高频点时，在末尾以 `**面试提示**：` 加一段。
